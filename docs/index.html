Ask everything. Generate nothing.

snap is a decision engine for LLM pipelines. Send one state with every question you have about it and get back typed answers, each with its full probability distribution, from a single pass over the model. Nothing is generated, so there is nothing to parse, retry or sanitize.

Built for the decisions inside your pipeline.

      
Anywhere you prompt a model for a label, a flag or a score and then parse what it wrote, snap is the shorter path. Six patterns, each with a real request and the response it got.

    

    

      

      

    

  







  

    

      
A chat model writes its answer. snap reads it.

      

        
At every step, a language model scores every token in its vocabulary as the possible next one. Those scores are the logits. Chat inference picks a token, appends it and runs the model again, once per token, until there is enough text for you to parse.

        
snap asks each question so that the answer is a single letter, runs the model once, and reads the scores of those letters directly.

    Question suffixes branch off it as a prefix tree, so any text they share is computed once, and repeat heads stay cached across requests.

    One batched decode
    
        
    Every question suffix decodes together in a single llama_decode call, one KV sequence per question. Six questions cost one pass, not six conversations.
    
        
    A startup probe picks the path each architecture supports. Nothing to configure.

    Read one position
    
        
    For each question snap reads a single row of logits, keeps only the option letters, merges their variants and softmaxes them into your distribution.
    
        
    coverage reports how much of the raw mass sat on your letters. snap calibrate fits a temperature per question type.

Prompt injection needs a voice. snap doesn't have one.

      
Injection works by getting a model to produce text you didn't intend: a leaked system prompt, a smuggled tool call, a link your UI renders. snap never produces text. What leaves the engine is a probability over options you wrote, in a JSON shape the server builds, not the model.

    


    

      

        
AttackLLM that generates textsnap

        
          

            Exfiltrate data through the response
            Possible. The response is free text.
            No text channel. Answers are numbers keyed by your option names.
          

          

            Smuggle a tool call or command
            Possible. The model writes the call.
            Nothing to execute. Your code maps a decided option to an action you wrote.
          

          

            Leak the system prompt or context
            Possible. It can be asked to repeat itself.
            Nothing is generated for it to leak into.
          

          

            Inject markup or links downstream
            Possible. Output gets rendered in a UI or an email.
            The response schema is fixed by the server.
          

          

            Break the output format
            Handled with validators, repair and retries.
            Can't happen. The model doesn't write the response.
          

          

            Argue the model toward a different answer
            Possible, and invisible in the output.
            Still possible, but bounded and measurable. Text in the state can only move probability between your options. It shows up as split confidence or low coverage, and allow_abstain gives it a way out. Threshold on it and route to a human.
          

        
      

    


    

      

        
On your hardware

        
A laptop, a VM, a Kubernetes pod or an air-gapped rack. One binary with llama.cpp compiled in, including a fully static Linux build. No Python, no runtime to patch.

      

      

        
No data egress

        
No API key, no telemetry, no third party processing your records. Weights are a GGUF on disk; after the first download snap runs offline. The daily release check prints to stderr and turns off with SNAP_NO_UPDATE_CHECK=1.

      

      

        
Auditable by design

        
Same input, same distribution. Log the full probability map with every decision, replay it later, and read x_snap for exactly what the engine did.

      

      

        
Open source

        
MIT-licensed Rust you can read end to end. Models come from a tested list, and calibration files refuse to load against a different model or prompt version.

Drop-in Jev. One endpoint.

      
snap speaks Jev's wire format on POST /v1/systemone. If a client already talks to Jev, point it at a local snap serve and it keeps working unchanged.

      
Extensions are optional fields a Jev client can ignore, and defaults preserve Jev semantics. Answers add status, confidence, coverage and the full probabilities on top of the Jev shape.

      

        
noulYes or no. Returns noul (P of yes) and boolean.

        
choiceOne of your options, 2 to 256. Returns the key and every option's probability.

        
scoreOrdered levels. Returns the winning level and an expected score in [0, 1].

        
numericA value in {min, max}, read over anchors plus below/above range.

        
allow_abstainAdds an __abstain__ slot, so "not enough information" is an answer.

Three commands to your first decision.

      
The first run downloads the model once (1.5 to 4 GB). After that, everything runs offline on your machine.

    

    

      

        
1
Install
One binary. Homebrew on macOS, a tarball everywhere else.

        

          
          
          
        

        

        

      

      

        
2
Serve
Pick a model from the tested set. The playground ships inside the binary.


$ snap serve --model qwen3.8-4b
# → http://localhost:8018/playground

        

      

      

        
3
Ask
Every question about the state, in one request.


$ curl -s localhost:8018/v1/systemone -d '{
  "state": "Checkout has been down for an hour.",
  "questions": {
    "urgent": {"type": "noul"},
    "team": {"type": "choice",
      "criteria": ["billing", "technical"]}}}'
